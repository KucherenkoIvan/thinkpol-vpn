## Goal
A DHCP client that rewrites `/etc/resolv.conf` in place while the node manages it doesn't lose its servers: the node takes the complete file as the new original.

## Scope
- Some writers truncate the file and then append to it: busybox udhcpc (`echo -n > $RESOLV_CONF`, then `echo nameserver … >> $RESOLV_CONF`), dhcpcd's `cat > /etc/resolv.conf`. The watch (`watch_linux.go`, `IN_CREATE|IN_CLOSE_WRITE`) wakes on the first close and `resolvConf.apply` reads the half-written file. It renames the managed file over it, so the writer's later appends land in the managed file, where `parseResolvConf` ignores them.
- Result: the original stays empty and the direct upstreams are lost until the next rewrite. With TP-115, an empty read while the first read is still owed also clears `dns_upstreams_stale`.
- Decide how to settle a write (for example a short quiet period after the last event before reading, or lines appended to the managed file taken as a new original), and test it with a fake writer that truncates then appends.

## Acceptance

## Notes
- Found by TP-115's round-1 correctness review (2026-10-21). The loss predates TP-115.
- From TP-128's round-1 review (2026-10-22), more cases with the same cause:
  - The 2 s poll can read the file empty mid-rewrite. The empty content is then recorded as the original, so `Restore` would put back an empty resolv.conf. (Fixed in TP-117: a write in place settles before it is read.)
  - While the first read is owed, a managed link's target that reads empty (`linkedOriginal`) counts as a good read, the same ambiguity TP-128 settled the other way for resolved's uplink file. (Fixed in TP-117: an empty target is no read.)
  - An empty /etc/resolv.conf can be a valid configuration, so the rule here needs its own decision in the dns package doc, not a copy of the uplink rule.
  - RESIDUAL-RISKS RR5 should name losing the original, not only stale upstreams.
- Decision (2026-11-12, after round 1; RR5 is decided on it): another program's write of /etc/resolv.conf is taken back by how it was written. A file renamed into the path (the change events since the last read are renames into it only) is complete and taken at once. Any other write settles: into the node's file in place, a new file created at the path (corrected in round 2, R2.1: it is created at the open, before its first write, so a new file is not complete), or where it can't be told (no file; the poll, which has no event; a bind mount). A settle reads the file once it has been quiet (no change event, the same file state) for 500 ms, and never later than 2 s after it began, so a writer that never goes quiet doesn't keep the OS on its resolver; Problem reports ErrUnprotected while another program's file is in place and for a 4 s hold (twice the cap) after each take-back of another program's write, one rule that doesn't model the writer (R3.1, replacing round 2's contended flag). Lines appended to the managed file join the original, as a backstop behind the settle (an in-place writer still appending after its settle ended, a hand append), not instead of it. Update reads the file under the lock and leaves a write in place to the watch; a failure then shows in Problem and the log. The first take-over at start is not settled (nothing the node wrote tells a write in progress from a finished one); the backstop catches an appending writer's later lines there. What is left: a writer that writes through one open file and pauses past the settle or the cap, or is mid-write at start, has the part read taken as the original (RR5). The empty-file rules are unchanged: an empty /etc/resolv.conf that stays through the settle is the new original; an empty link target while the first read is owed is no read.
