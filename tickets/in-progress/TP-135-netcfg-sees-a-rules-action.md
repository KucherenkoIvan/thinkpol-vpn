## Goal
The Linux configurator's check of its own policy rules notices an owner's rule that someone turned into `blackhole`, `prohibit` or `unreachable`, and puts it back, as it does for any other change.

## Scope
- `ruleOf` (`netcfg/rules_linux.go`) says it rejects "another … action", but vishvananda/netlink's rule dump never fills the rule type, so it can't see one: a rule changed from lookup to blackhole looks like the configurator's own and stays.
- TP-091 reads rules from a raw `RTM_GETRULE` dump that carries the action (`dumpRules`/`parseRawRule`), and (after its round 3) one shared judge of "a plain rule" (`plainRule`) for the mask, suppress and action rules. Read the configurator's survey through `dumpRules`/`parseRawRule` too, so a changed action counts as foreign and is repaired, and the list of selectors netcfg never sets exists once: `ruleOf` (and its netlink.Rule field list) goes.
- Say in the netcfg doc what the survey compares.

## Acceptance
- [x] lab: an owner's lookup rule replaced by `ip rule add … blackhole` at the same priority and protocol is put back by the next apply, and a test fails if the action isn't read
- [x] one list of the selectors netcfg never sets: `ruleOf` is gone, and the configurator and diagnostics both read rules through `parseRawRule`
- [x] `make lint`, `make test`, `make lab-test` pass

## Notes
- From TP-091's round-3 and round-4 design reviews (2026-10-23). Predates TP-091.
- **Slot (pre-M2 phase, 2026-10-24).** Wave 1, macOS lane.
- **Rule dumps split over several reads (R2.5, 2026-10-29; corrected in round 3).** No kernel source was at hand; from netlink semantics and fib_rules.c as remembered: `fib_nl_dumprule` → `dump_rules` walks the family's rule list under RCU, resumes each part at the list index saved in `cb->args`, and neither sets `cb->seq` nor calls `nl_dump_check_consistent`, so a rule dump never carries NLM_F_DUMP_INTR. A rule inserted ahead of the resume point between two parts repeats the boundary rule (a phantom duplicate); one deleted ahead skips a rule (a phantom miss). Round 2's Notes said the next Watch-triggered Apply recovers a miss: untrue, since Watch reacts to neither someone else's insert nor a delete of a rule not ours, and they left out Close, where `removeOwned` would leave a skipped rule of ours behind for good. Since round 3 (R3.1) `dumpRules` takes dumps until two in a row hold the same messages (order ignored), up to `dumpRetries` (5), and fails with `errDumpsDisagree` otherwise, so repeats and misses are gone for every caller (Apply, Close, Survey, Inspect, the stray check), short of two races giving the same wrong dump twice in a row. `surplusRules` still decides once per distinct message (key: the message without the kernel-only flags, as `sendRule` sends it), as defence in depth. RR54 (RR53 before the merge with TP-124) is not concerned. Round 4 (R4.1, R4.2): the dumps pause 1, 2, 4, 8 ms between tries and compare messages without the kernel-reported flags; Close no longer takes agreeing dumps but deletes our rules from single dumps until one shows none (a repeat's second delete finds ENOENT or takes another rule of ours; a skip shows in the next dump), and goes on with routes and links whatever the rules do. Two dumps that agree and are both wrong are RR55.

Round 5 (2026-10-29): correctness (paranoid, fix first) review.
- [ ] R5.1 (paranoid #1) On Linux 4.11–4.16 a skipped stray check (R4.3) leaves our rules stored with protocol 0: nothing judges them again (the next add of the same rule gets EEXIST, so ErrConflict and a rollback before the check), Close doesn't see them as ours, and every later Apply fails until reboot. - [ ] R5.3 (paranoid #4) Close's rules loop stops at the first dump that shows none of ours, so one skipped rule at a part boundary ends it early. End only after two empty dumps in a row; fix the doc sentence ("One a dump skips shows in the next").
