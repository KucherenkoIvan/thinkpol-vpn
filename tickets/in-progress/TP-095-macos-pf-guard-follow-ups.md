## Goal
Tidy up the macOS pf IPv6 leak guard's failure paths and test nits left from TP-078 and TP-092 device sessions and review.

## Scope
1. A load that `saneRules` or the table check refuses: decide between flushing the anchor and keeping the unverified rules (they still block IPv6), document the choice in DESIGN.md, and cover it with a test.
2. `applyGuard` skips the warn window for an Apply that failed because its context was cancelled (`routetable.go` around 546–560).
3. A success after silenced failures logs the suppressed count once.
4. The fake's ICMPv6 names for 131 and 132: check pfctl's icmp6 type table (first match per number) and fix.
5. Delete `TestEveryLoadCarriesNoOptimizer` (a source scan; the fake's reordering already proves the behaviour).
6. Delete `TestApplyLoadsUnoptimized` and `TestTheFakeOptimizesALoadWithoutNone`. They re-prove `TestApplyPutsTheGuardInPlace` and `TestAnOptimizedLoadIsRefused` now that the fake reorders loads without `-o none`, and what's left of them asserts call sequences.
7. Redaction: the guard's WARN logs pfctl's raw error, and a `saneRules` error can quote a DNS upstream's address, while the route table's own warnings redact (`path.RedactError`, because logs may leave the device). Either redact, or keep the rule text on purpose (it is what diagnosed TP-092), say why in a comment, and redact the addresses in it.
8. Make the rate limiter a small reusable type (`warnLimit`: allow/reset), and use it for the route table's re-apply warnings too (`routetable.go` around 621, 639 and 729), which warn every `RetryAfter` forever.
9. Comments and DESIGN.md state constraints, not history:
   - `guard_darwin.go:201-205` and `:26-27`;
   - the fake's `withoutNone` comment and the dated "`from any to`" comment;
   - DESIGN.md:157's parenthetical with a session date: the evidence belongs in TP-078/TP-092.
   Fix the fake's comment, which says only the listing is reordered (`basic` reorders the ruleset pf evaluates). Rename `fakeOptimize`, or say it reproduces only the reordering seen on the device.
10. `Enforcer.now`: declare it with the other construction-time fields, and set it before the watcher goroutine starts (for example an unexported `openWithClock` that `OpenWithGuard` calls). Use one style in `export_test.go`. The rate-limit test advances by the limit itself, not by `RetryAfter * 12`.

## Out of scope
Device runs on a network with native IPv6 (TP-096).

## Review findings
Round 1 (2026-10-22): correctness (fix first), design (fix first), second opinion (fix first).
- [x] R1.1 DESIGN.md (~158, "The leak guard on macOS"), the Apply comment (`guard_darwin.go` ~139-144) and the scope-1 Log line say a refused load isn't enforced ("pf isn't enabled for them"). That is only true before the first good load. A reload has already replaced the last verified guard in one pf transaction, and pf is on under the guard's earlier reference, so pf enforces the unverified rules (as `TestARefusedLoadStaysInPlace/after a good load` asserts). Say so: a load pfctl takes but whose read-back is refused stays in place and the apply fails and is retried; pf enforces it on the guard's existing reference after an earlier good load, and not at all before one; its rules are all `quick` and end in the block, so a reordered listing is never wider than the rules written, and a table pf holds wider than the one loaded is enforced as it is until a retry reads the anchor back whole. Keep the behaviour: reloading the last verified guard was considered and rejected (it guards the previous Exempt, so after a preset moves X from direct to tunnelled it would exempt X around the tunnel; its own read-back can be refused the same way; a wider table needs a root process changing the anchor between load and read-back). Write that reasoning down where the decision lives, and add a Log line saying the earlier wording was corrected.
- [x] R1.2 `warnLimit.allow` keys only on time: one warn opens a minute in which a different failure is counted and never logged, and if it clears inside the window only `suppressed=N` reaches the log. A refused load's quoted rule (scope 7) is the line this loses. Let a warn through when its (redacted) text differs from the last one warned at that site; a test with two different failures inside one window.
- [x] R1.3 `subscribe` and `subscribeGuard` (`routetable.go` ~676, ~699) warn on a `Watch` that failed because the watcher's context was cancelled (`rewatch` and `ctx.Done()` both ready). Warn only while the context is live, as scope 2 does for the guard's Apply.
- [x] R1.4 A successful `Enforce` doesn't reset `reapplyWarn`, so a new re-apply failure within a minute of an old episode's warn is held back as the same failure. Reset (and log held-back) when the routes' apply succeeds in `apply`, not only in `reapply`.
- [x] R1.5 `reapply` (`routetable.go` ~745-750) sends a failure wrapping `ErrUnsupported` through the limiter; held back within a minute of an earlier warn, its text is never logged because `watch` then returns for good. A terminal failure always warns.
- [x] R1.6 Redaction eats pfctl's line numbers: `stdin:5: syntax error` matches `addrPattern`'s last alternative (`path/link.go` ~320-323) and warns as `stdin<addr> syntax error`, losing which rule pfctl rejected. Keep `stdin:N:` readable without letting any address through (e.g. reword pfctl's prefix in `detail()` before redaction, or tighten the pattern with tests that every address form in the existing redaction tests still goes); a test on a pfctl syntax-error line.
- [x] R1.7 Nits: `export_test.go` `var ClearWith = clearWith` → a func like the others (Log line "helpers are all functions" is false today); `allow`'s second result `suppressed` → `heldBack`; `cleared` → `logCleared`; `warnLimit`'s mutex protects nothing (applyGuard runs under `e.mu`, the rest on the watcher goroutine): drop it or state the constraint; the `saneRules` comment (`pfctl_darwin.go` ~463-465) describes another package: state it as a constraint ("whoever logs this error must redact its addresses"); `guard_test.go` ~541 runs Subscribe steps on `context.Background()` and leaks fake Watch goroutines: `t.Context()`; `guard_test.go` ~455 and ~618 drive `GuardApply` with the watcher running: pause it as the per-site test does; `TestALoadPfDoesntHoldFails` and the "the first load" subtest of `TestARefusedLoadStaysInPlace` check the same thing: fold or drop one.
