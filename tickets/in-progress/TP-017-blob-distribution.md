## Goal
Nodes get the list files (and later releases) referenced by their map from peers, without any outside server.

## Scope
- Simple request/response service on overlay addresses: fetch blob by hash.
- Verify the hash, cache in the state dir, serve cached blobs to peers.
- Fetch on map change; keep serving the previous version until the new one is verified.

## Acceptance
- [x] in the lab, a device without the list fetches it from a server node — `lab/blobs_test.go` `TestBlobDistribution` (map `lab/maps/blobs.yaml`): device-a's section names `geoip:ru` (built by `dev lists build` from a CSV fixture), server-1 runs in server mode with the list seeded in its state directory; device-a logs `blob fetched … peer=<server-1>` (served by server-1's sandboxed worker) and keeps it as `blobs/<sha256>` (0600, directory 0700); server-1's state directory is unchanged
- [x] a corrupted blob is rejected and fetched again from another peer — same test: server-2 (first in device-a's peer order) answers on its overlay address with junk of the right size; device-a logs `blob rejected: the peer sent something else; trying another peer … peer=<server-2>`, then fetches from server-1. A byte flipped in device-a's stored copy is rejected at the next start (`stored blob rejected`) and fetched again. Unit: `TestATamperedBlobIsRejectedAndFetchedFromAnotherPeer`, `TestATamperedStoredBlobIsReplaced`, `TestAPeerAnnouncingTheWrongLengthIsRejected`

## Notes
**Decisions:**
- **Transport: TCP on overlay addresses, not a path-layer frame kind.** The ticket's "request/response service on overlay addresses". Inside WireGuard the far end is the peer WireGuard authenticated (cryptokey routing), TCP gives reliability, flow control and resumption for free, and the traffic is ordinary tunnel data to a censor. A path-layer frame kind would reach link neighbours (relays without WireGuard peers too) but would need its own reliability and chunking; not worth it while every node that holds or needs blobs has WireGuard peers (devices ↔ servers; the controller's node, M4, is everyone's peer). Port `blobs.Port` = 4717 on every overlay address. Both sockets are bound to the TUN (`SO_BINDTODEVICE`): Linux's weak host model would otherwise let a LAN neighbour reach a device's overlay address from outside the tunnel and fingerprint the port; dials can't leave another way either. `bind_other.go` refuses until TP-019/TP-047 bring `IP_BOUND_IF`/`IP_UNICAST_IF`.
- **Protocol** (`internal/dataplane/blobs`, doc.go): request `"TPB" | 1 | sha256[32] | offset[8 BE]`; response `status[1]` (0 ok, 1 not here, 2 busy, 3 bad request) then for ok `length[8 BE]` = size − offset and the bytes. One request per connection. A server answers only for blobs it holds, all of which a signed map of its space listed (wanted now, or a stand-in kept from the previous map until its successor is verified): unknown and not-held are the same "not here", so no oracle beyond the availability set. The client knows the size from its own map and refuses any other length (protocol violation = rejection). Uncompressed on the wire (lists are ≤ ~300 KB; hash over the uncompressed bytes either way).
- **Checks** (`blobs.Check`): size and SHA-256 against the map's `BlobRef`; for `BlobGeoIP` also `lists.Decode` (TP-016). Unknown kinds are held and passed on by hash. A blob that matches its hash but doesn't decode is the map's fault (`ErrUndecodable`): marked failed, not retried until the map changes. Every blob is checked whenever it is read: from a peer, from the device's disk, from a server's seed (supervisor and worker both).
- **Who holds what** (`blobs.PlanFrom`): a device its section's blobs (named), a server every blob of the header (the availability set it passes on), named where its section names them. A section blob the header doesn't list with the same kind and size is dropped (readers don't check it, `Build` does). Peers: the section's WireGuard peers in map order, at their overlay addresses inside the space's networks (IPv4 first, IPv6 only while the overlay carries it); the service listens on the node's own overlay addresses.
- **Cache location** (DESIGN "Node safety", `internal/agent/state.go`): `blobs/<hex sha256>` in the state directory, under its rules (owner, no group/other write, no symlinks; files 0600 written aside, fsynced, renamed, dir fsynced; `trustedDir.mkdir/writeFile/remove`). **Devices write it** (`diskBlobs`): the lists their rules use are needed from the moment the device starts, before any peer is reachable; pruned to what the map names once the map's blobs are all held, and the directory removed with the last blob. **Servers only read it** (`seedBlobs`): seeds put there by provisioning (or by hand: `install -m 600 ru.geoip /var/lib/thinkpol/blobs/$(sha256sum ru.geoip | cut -c1-64)`); what a server fetches stays in its worker's memory: it uses no list itself and fetches the set again after a restart, so per DESIGN rule 5 it keeps nothing it could do without. The supervisor reads the seeds of the current header and sends them in `WorkerConfig.Blobs` (config version 2; a sealed memfd when large); the worker's store is that set in memory (`seedStore`). Seeds are read when a map is applied: add them before the map that names them. The content is public lists the map already names by hash, so the disk reveals nothing the envelope doesn't.
- **Keeping the previous version** (`Service.Latest`): when a map replaces a list, the old blob stays held (and served, and on disk) until every blob the new map asks for is held; then the rest is dropped and the store pruned. Named blobs stay as stand-ins while the new map names a blob of the same kind and name (one per name: a newer held one replaces it); unnamed ones (a server's) for one map. A map that removes the node empties the plan: listeners close and the device's lists are pruned.
- **Bounds** (`blobs.Limits`, defaults): 16 MiB a blob, 64 MiB the current map's blobs together (beyond: skipped, warned, `Status.Skipped`; stand-ins can add about as much again until replaced); serving: 16 connections, 2 per peer address (more → busy), 2 MiB/s shared token bucket, 30 s idle timeout per read/write; fetching: one blob at a time, one peer at a time, 15 s dial timeout (room for WireGuard's handshake), a transfer that breaks after making progress resumes from its offset (up to 3 times) from the same peer, rounds with something missing back off 2 s → 1 min, a new map starts a round at once; the store is asked once per blob per map. Memory: a client buffers at most the blob's size from the map.
- **Status** (`blobs.Status`): counts only (wanted, held, skipped, failed, fetched, loaded, rejected, store rejected, served, served bytes, not here, busy), nothing from the map or about peers, so TP-022/TP-041 can expose it; the debug status line carries `blobs_wanted/held/rejected`. Logs: `blob fetched`/`blob rejected …`/`stored blob rejected …` with the hash's first 6 bytes, kind, name and the peer's node id (local logs only).
- **devmap** (TP-004's gap): spec `lists: [{name, file}]` (file relative to the spec's directory, `${VAR}` allowed) and per node `lists: [ru]`. `devmap.ReadLists(spec, os.ReadFile)` (called by `dev map build`) reads each file, checks `lists.Decode` and the size limit, refuses two lists with the same content; `Plan` puts every list unnamed into the header and the named refs into the sections of the nodes that use them. `reference.yaml`, `doc.go` and the reference golden updated.

**Tests:** `internal/dataplane/blobs` over loopback standing in for the overlay (fetch, tampered peer then a good one, tampered store, store only, previous version until the successor is verified with the store not pruned early, a relay holding and passing on the whole set incl. an unknown kind, not-here/bad offset/other version/offset reads, resume after a hang-up, wrong announced length, limits, undecodable list not retried, busy past the per-peer limit, the rate limiter, `Check`, `PlanFrom`, status quoting nothing); `-race -count=30` clean. `internal/agent`: `RunDataPlane` on virtual TUNs with services over loopback (a server fetches the header set from a device's disk store; removal empties the device's plan and removes `blobs/`), a server's worker serving its seed to a device (`TestServerSeedsItsWorker`), `diskBlobs` round trip/prune/foreign names/modes/symlink and writable-directory refusals, `seedBlobs` with a tampered seed, `WorkerConfig` round trip. `internal/devmap`/`cmd/thinkpol`: spec errors with positions, `ReadLists`, `dev lists build` → `dev map build` → `inspect`.

**For downstream tickets:**
- **TP-015 (rules):** thread the agent's `*blobs.Service` (`DataPlane.Blobs`) to the rule compiler: `geoip:<name>` → `Service.Latest(netmap.BlobGeoIP, name)` returns the current map's list, or the previous one while the new one isn't verified yet (bytes already checked; `lists.Decode` them); `Service.Changed()` is signalled whenever the held set changes, so recompile then. A rule whose list isn't held yet (first start without peers) must fail safe (TP-015 decides: match nothing → later rules, i.e. the tunnel). Devices only hold their section's blobs: the builder must name in a device's section every list its rules use.
- **TP-018 (route table):** nothing new beyond TP-016's notes; the direct set changes when `Changed()` fires with a new list, so route updates must be incremental or atomic.
- **TP-044 (signed updates):** reuse the service for release blobs: a new `BlobKind` (old nodes hold and pass unknown kinds by hash) and a release key check after `Check`. Releases are tens of MB: raise `Limits.MaxBlob`/`MaxHeld` for that kind, and stream to disk instead of buffering in memory (the protocol already resumes from an offset); a server's seeds travel in its worker's config today, which suits lists, not releases (keep releases out of `WorkerConfig.Blobs`, e.g. a memfd per blob or the supervisor serving them).
- **TP-037 (gossip/persisting):** if servers should keep fetched blobs across restarts after all, the worker needs a way to hand checked blobs to the supervisor (a new ipc kind), which writes `blobs/` like `map.bin`; today servers only read it.
- **TP-036/TP-038 (publishing, provisioning):** some node must hold every published blob: the controller's node seeds its own `blobs/` (it's every node's WireGuard peer), provisioning may seed servers. Header and section blob refs are `netmap.BlobRef{Kind, SHA256, Size, Name}` (header unnamed).
- **TP-019/TP-047 (macOS, Windows):** implement `bindTo` in `internal/dataplane/blobs` (`IP_BOUND_IF`/`IPV6_BOUND_IF`, `IP_UNICAST_IF` + an inbound check) — until then the service refuses to listen or dial there.
- **TP-040 (guests):** blobs are per space: a guest space's seeds belong in its own directory (e.g. `guests/<space-id>/blobs/`), read by `seedBlobs` for that space's worker only.
- **TP-022/TP-041:** `Service.Status()` for the local API and telemetry.
