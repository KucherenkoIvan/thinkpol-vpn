## Goal
Nodes that allow egress forward a space's internet traffic, IPv4 and IPv6, and nothing leaks across spaces.

## Scope
- Forwarding inside the space's namespace, out through its veth; masquerade once in the root namespace (nftables via a pure-Go library such as `google/nftables`).
- IPv6: NAT66 when the VPS has IPv6, otherwise reject with ICMPv6 unreachable so clients fall back fast.
- Nodes without egress drop internet-bound traffic.
- Full cleanup on stop.

## Acceptance
- [x] in the lab, a device fetches from the `internet` target through `server-2` (IPv4, and IPv6 where the lab has it): `lab/egress_test.go` `TestEgressThroughAnExit`, every server in server mode; device-a's chain ends at server-2, relayed by server-1's worker; `curl` over IPv4 and IPv6 returns the page and ping answers, and a capture at the internet node sees requests only from server-2's own two addresses. On a VPS without IPv6 (server-2's IPv6 default route deleted), IPv6 gets ICMPv6 "no route" at once and no IPv6 packet reaches the internet, while IPv4 goes on
- [x] an egress-off node refuses the same traffic: same test, server-2's egress turned off while device-a keeps its older map (same link secrets, `-secrets-seed`) and still sends its internet traffic to server-2: no fetch succeeds, nothing reaches the internet, the overlay through server-1 to server-2 still answers. Root-namespace rules on their own: `internal/agent/supervisor` `TestEgress` (lab node): a space with egress reaches a namespace behind the uplink over IPv4 and IPv6 masqueraded to the uplink's addresses, an overlay source SNATed first; a second space on the same node without egress gets nothing out (not through the first's egress either) but the endpoint its section dials, and only on that port; egress off closes it; a LAN namespace's forwarded traffic keeps its source (no masquerade of non-transit sources); forwarding is turned on and restored by `Close`

## Notes

- **Done in TP-014 (2026-10-12):**
  - **Root table** (`supervisor/isolation_linux.go`, `inet thinkpol-supervisor`, rebuilt from every slot in one flush per `SetSpaces`): `antispoof` (prerouting, raw−10: a space's packets with any source but its transit address dropped *before conntrack*; replaces `antispoof_fwd`/`antispoof_in`); `ct_pre` (raw: zone N+1 for a space's packets to its root end's transit address and its broadcasts/multicasts); `ct_out` (zone N+1 for what the root sends a space); `forward`: `iifname != tp-space* oifname tp-space* ct state established,related accept` → `oifname tp-space* drop` → `iifname tp-space*` to a blocked destination drop (`egressBlocked`: 0/8, 127/8, 169.254/16 incl. metadata, 224/3, ::/127, ::ffff:0:0/96, fe80::/10, ff00::/8, fd00:ec2::254, plus both transit ranges) → per slot with egress `iifname tp-spaceN oifname <uplink> meta nfproto ipv4|ipv6 accept` → per slot per dial `iifname tp-spaceN daddr A meta l4proto tcp|udp th dport P accept` → `iifname tp-space* drop`; `input` unchanged; `postrouting` (nat, srcnat): `oifname != tp-space* ip saddr <TransitIPv4> masquerade`, same for IPv6 (NAT66). Provider-private ranges (RFC 1918, ULA) are not blocked: the lab's internet is one.
  - **Conntrack zones changed (deviates from TP-009's note).** Forwarded flows (egress, dials) stay in zone 0: their replies arrive on the uplink, where nothing can tell the zone before the lookup, and must find the flow to be un-NATed. google/nftables can't set an original-direction-only zone (`ct original zone set`), and `fib daddr type` (to zone only what is for the root itself) is missing from the lab's kernel, so zones cover a space's traffic with its root end and the root's traffic to it. Anti-spoof before conntrack is what makes zone 0 safe: a space's packet always has its own transit source, so it can match only its own flows. "Established replies by zone" became "established replies to the space's veth", which de-NAT routes by the flow's original source.
  - **Space table** (`supervisor/egress_linux.go`, `inet thinkpol-space` inside each space's namespace, installed by the supervisor through `nftables.WithNetNSFd` when the namespace is wired and again on an egress change, never by the worker): `forward` policy drop: established accept, `oifname veth0 meta nfproto <fam> accept` per family with egress, `reject with icmpx no-route` for a family the uplink lacks (only when the space has egress); `postrouting` SNAT to the transit address for any other source leaving veth0. The namespace's `ip_forward`/`forwarding` are on in `baselineSysctls`; the table decides. Deviation from TP-013's note: the SNAT is the supervisor's, not the worker's (it knows the transit addresses and which families the uplink has; the worker could change it anyway, and the root table enforces the same egress again).
  - **Root forwarding** (`rootForwarding`): turned on per family when some space has egress or a dial of it; `accept_ra` 1 → 2 on every interface (and `default`) before IPv6 forwarding; everything changed is restored on `Close` (a SIGKILLed supervisor leaves it on; the next one sees it on and changes nothing). A failure is a warning: egress then fails closed.
  - **API.** `supervisor.Space{…, Egress{Uplink, IPv4, IPv6}, Dials []netip.AddrPort}`; `SpaceTableName`. `egress.FindUplink() (Uplink{Name, IPv4, IPv6}, error)` (`internal/dataplane/egress`, desktop Linux; `ErrNoUplink`, elsewhere `ErrUnsupported`): the link of the lowest-metric IPv4 default route (IPv6's on a v6-only node); IPv6 only when a v6 default route leaves by the same link and it has a non-link-local address. The agent (`serverSpaces.egress`) finds it again on every map; no uplink: no egress, warned. `Dials` = every endpoint address of the section's links. `router.Table.Forward []*Egress` (egresses that also deliver non-overlay destinations; never IPv4-mapped, never other overlay addresses); `dataplane.EngineConfig.Forward` + `Status.Exit`: the overlay device forwards when the section is a server's with `AllowEgress` and `Forward` is set, which only `ServeSpace` (the worker) does: a server in `-mode device` is never an exit (its host would forward into its own LAN). Chain-exit devices never forward.
  - **Logs and status:** `map applied` says `egress=on|off` and, with egress, `uplink=<if> egress_ipv4=on|off egress_ipv6=on|off`; `Status.Exit` is a bool; counters only. No destination is logged or counted anywhere (S4).
  - **devmap:** a device's `chains: {name: exit}` and `rules: [text]` in the spec (Build checks exits and chains), printed by inspect; `dev map build -secrets-seed` derives link secrets from a seed so builds of one spec share them (lab tests only). `lab/maps/egress.yaml`. `lab/ingress_test.go` runs server-1 in server mode.
  - **Not done, with reason:** device-mode egress (a Linux device or a `-mode device` server as an exit): the ticket scopes egress to the server's namespaces, and devices can't allow egress (Build refuses). An uplink change between maps (DHCP moving the default route) is picked up only with the next map. Guests on a shared node (TP-040) aren't servable yet, so "a space without egress on a shared node can't use another space's egress" is proven at the supervisor level (two spaces, `TestEgress`), not end to end.
  - **Checks (2026-10-12, after merging TP-015, TP-022, TP-017):** `make lint`, `make test`, `make test-race` (one load flake in udp `TestSenderChurnIsBounded`, passing alone), `make lab-test`: `lab` green incl. `TestEgressThroughAnExit` and `TestIngressOffAdmitsOnlyServers` (server-1 in server mode); in-node, two failures under a host shared with other labs, both green alone: netcfg `TestApplyThenCloseRestoresEverything` (untouched) and `TestSharedListenerThroughput` (loss at the handoff 4–18% on this branch and on `rewrite` alike, back to back). - **For TP-018 (route table):** a device sends internet traffic into the TUN only through routes; the lab test adds `ip route add <internet>/32 dev thinkpol0` by hand (see `lab/egress_test.go`): replace that with the route-table mode and drop the manual routes. The exit's own socket traffic is unaffected (it is in the worker's namespace).
- **For TP-030 (chains):** an exit is a server in server mode with `AllowEgress`; nothing more is needed on the exit side. Multi-hop: relays' workers dial the next hop through the root namespace by the dial exception (`Space.Dials` = the section's link endpoints), whatever their egress; a middle hop needs no egress. A chain whose exit's uplink lacks IPv6 gets ICMPv6 no route, so the device's IPv6 falls back to IPv4 by itself.
- **For TP-040 (grants):** `Space.Egress` for a guest must be the grant's egress (at most what the node allows), not the guest map's `AllowEgress`, both in the supervisor's `Space` and in the worker's section (the engine's `Exit` follows the section: set the guest section's `AllowEgress` from the grant before handing it over, as TP-013's note says for ingress). Per-space egress caps: tc on the veth (`WorkerInfo.Link`) fits here; the root table's per-slot rules are where a per-space egress counter would go.
- **For TP-038 (provisioning):** a container runtime's or host firewall's `FORWARD` drop (Docker, ufw) still wins over the supervisor's accepts: `node add` must allow forwarding from `tp-space*` to the uplink (or not install such policies). Provider-private ranges are reachable from exits; block them there if a provider's network needs it.
- **For TP-021 / TP-048 (leaks, kill switch):** an exit without IPv6 rejects IPv6 with ICMPv6 no route; the device must still block IPv6 outside the tunnel itself.
