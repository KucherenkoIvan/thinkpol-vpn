## Goal
On Linux devices, `direct` destinations go straight out and everything else enters the tunnel, using the OS routing table.

## Scope
- Install `direct` prefixes via the physical gateway; send everything else into the TUN (split defaults such as `0.0.0.0/1` + `128.0.0.0/1`, and the IPv6 equivalents).
- Always keep entry nodes' endpoints outside the tunnel (routing-loop prevention).
- Watch for physical gateway changes (netlink route events) and re-apply.
- Full cleanup on disconnect.

## Notes
- netcfg (TP-007) manages the main table only: per-space namespaces each have their own. If enforcement needs policy routing (ip rules + extra tables), add `Table` and rules to the netcfg port here. See TP-007's Notes for `DefaultRoute`, split defaults and delete-then-add on route changes.
- **From TP-016 (lists):** `lists.Set.Prefixes()` is already the merged minimal CIDR list (overlapping and adjacent merged), IPv4 then IPv6. RU is ~23k prefixes (DB-IP Lite 2026-10: 12,895 IPv4 + 10,088 IPv6). Lists never hold IPv6 inside `::ffff:0:0/96`, so no IPv6 route can capture IPv4.
- **Any coarsening (e.g. a route budget for Windows, TP-047) may only shrink the direct set, never grow it:** drop or split direct prefixes, never widen one. Growing would send foreign traffic outside the tunnel, in the clear in front of the censor; shrinking only sends some domestic traffic through the tunnel. Put it in `internal/lists` with a test that the result `Minus` the original is empty.
- From TP-006: links' sockets are marked by the transport adapter (`udp.Options.Control`), never by WireGuard (no `fwmark` on any WireGuard device; the path layer's Bind refuses marks). Linux: `SO_MARK` plus an `ip rule` sending marked traffic to the main table. Darwin: `IP_BOUND_IF`/`IPV6_BOUND_IF` to the physical interface. Windows: `IP_UNICAST_IF`. TP-011 builds the Registry with that Control.
- **From TP-017:** a device's direct set changes when a list arrives or is replaced (the engine recompiles on the blob service's change signal, `Engine.ReloadRules`), not only on a new map: route-table updates must be incremental or atomic. During a list's replacement the previous version stays in force (`EngineConfig.StandIn`) until the new one is verified, across restarts too (the device's `blobs/index`).

**Done in TP-018 (2026-10-12).**

*Layout (Linux, per family; DESIGN.md "Routing rules and DNS", route table on Linux), after the review:*
```
rule 5300: to <overlay network> lookup main suppress_prefixlength 0          proto 86
rule 5300: to <trusted on-link subnet> lookup main suppress_prefixlength 0   proto 86   (mirrors main's proto kernel routes)
rule 5301: not fwmark 0x7470 lookup 29808 (0x7470)        proto 86
table 29808, proto 86:
  default dev thinkpol0                 (IPv6 only while the overlay carries IPv6)
  unreachable default metric 2048       (both families)
  throw <direct prefix>                 (the rules' direct set, minimal)
  throw <endpoint>/32, /128             (every endpoint the section dials)
```
- Policy routing instead of split defaults in main: direct traffic and endpoints are *thrown* to the main table, so they follow whatever physical default route is there. Nothing names the gateway: DHCP renewals, roaming and interface changes need no route change (the lab moves the gateway and nothing in the table changes), and there is no delete-then-add window. Marked sockets (the links') skip the table. The endpoint throws make links bypass the TUN even unmarked and keep strict `rp_filter` working (replies from an entry pass the reverse-path check through the main table); the cost is that any traffic to an entry's address goes around the tunnel, not only the link's.
- Only the overlay and the trusted on-link subnets are looked up in main ahead of the tunnel (B2, TunnelVision): `routetable.TrustedOnLink` takes on-link subnets inside `lists.Local()` and other IPv4 /24-or-longer and IPv6 /64-or-longer ones, so a huge DHCP netmask (an "on-link" 8.0.0.0/8) doesn't open a hole. These rules ignore main's default routes: a prefix whose own route is gone (a TUN that lost its IPv6 addresses going down) would otherwise find main's default and leave in the clear; the namespace test caught exactly that. Main's other routes (option-121 classless routes, another VPN's /1 splits, RA route information) apply only to what the table throws and to marked sockets.
- Nothing leaks around the tunnel: whatever the TUN can't take meets an unreachable default, IPv4 and IPv6 (B1): the TUN down or gone, IPv6 off in the overlay (MTU < 1280, or no IPv6 address), the kernel dropping the TUN's routes on an MTU change or a link going down before the next re-apply. **Changed in review:** IPv4 now has the fallback too. After a crash (kill -9) both families therefore stay blocked but for direct destinations until the agent starts again, connected or not (B3 removes it on any start); with D4's kill switch off that is stricter than "traffic flows when the tunnel is down" for the time between a crash and the restart. TP-046's unit restarts the agent; TP-048 decides whether a deliberately stopped service with the kill switch off must ever leave it (a clean stop always removes it).
- Re-applies (B1): the watcher re-applies after link events (any link added, removed or changing flags; wireless events, which change no flags, are ignored), changes of main's kernel (on-link) routes and of no owner's default routes, and removals of our own routes and rules; every `routetable.Backstop` (1 min) anyway, and every `RetryAfter` (5 s) while the last attempt failed. `Status.RouteTable{Enforced, Error}` (fixed texts `routetable.ErrorApply`, `ErrorReapply`) and the agent's health problem `route_table_not_enforced` (down) say when it isn't in place; `RulesAhead` and the problem `policy_rules_ahead` (degraded) when other software's rules come first (Tailscale-style, priorities below 5301), also as `route_table.rules_ahead` in `thinkpol status`.
- Mark and table 0x7470, priorities 5300/5301 (`routetable.Mark`, `Table`, `PriorityMain`, `PriorityTunnel`).

*Ports and packages:*
- `netcfg`: `Route.Table` (0 = main), `Route.Type` (`RouteUnicast`, `RouteThrow`, `RouteUnreachable`), `Config.Rules []Rule{Family, Priority 1–32765, Dst, Table, Mark, Invert, SuppressDefaultRoutes}`, `Configurator.Watch(ctx) (<-chan struct{}, error)` (coalesced signals: link events, main's kernel on-link routes, no owner's default routes, the owner's own routes or rules deleted, also by its own Apply) and `Configurator.Survey(ctx) (Survey{OnLink, ForeignRules}, error)`. After adding rules, netcfg checks they came back with its protocol; a kernel that dropped it (before 4.17) gets them deleted again and the Apply fails with `errors.ErrUnsupported` (B4, `strayRules`, unit-tested). Routes are dumped across all tables by protocol; rules carry `FRA_PROTOCOL` (Linux ≥ 4.17) and are reconciled, taken over after a crash, undone and closed like routes. `Validate` checks tables (no 253–255 by number), types and rules. Tests: `policy_linux_test.go` (apply/repair/close, cancelled Apply, takeover of rules, Watch).
- `dataplane/routetable` (new): `Want{TUN, Direct *lists.Set, Bypass []netip.Addr, IPv6}`, `Config(Want) netcfg.Config` (pure, unit-tested anywhere), `Enforcer` (`Open(configurator, log)`, `New(log)` = `netcfg.New(OwnerRouteTable)`): `Enforce` skips an equal Want, pauses the watcher while it applies (its own events would only slow it), re-applies after `Watch` signals (200 ms debounce), `Status{Routes, LastApply, Reapplies}`, `Close` removes everything. `SocketControl()`: `SO_MARK` 0x7470 on Linux (a socket it can't mark fails to open), nil elsewhere.
- Engine: `EngineConfig.RouteTable` (interface: `Enforce`, `Status`, `Close`; owned once `NewEngine` succeeds, closed first in `Close`), `StepRouteTable`, `Status.RouteTable{Enforced, Error, Routes, LastApply, Reapplies, RulesAhead}`, the overlay networks in the Want. Apply, `SetRules`, `ReloadRules` and `Close` are serialized by their own mutex and let go of the state lock while the OS table changes, so `Status` and `Inbound` never wait seconds for it; `SetRules` and `ReloadRules` run under a context `Close` cancels. Wherever the rules recompile (Apply, `SetRules`, `ReloadRules`): direct prefixes the new rules drop are removed *before* the router's table changes (`shrinkRoutes`), the new set goes in after (`growRoutes`); a failed removal falls back to nothing direct (everything into the TUN, where the router drops what it calls direct), and the next Apply retries. Endpoints come from the section's dialed links.
- Agent: a device that starts disconnected or removed first removes what a crashed run left (`routetable.Clear`, B3). Device mode sets `DataPlane.RouteTable` (an Enforcer next to the overlay's configurator; its construction failing is `StartError{Step: "route table"}`); `Transports(markSockets bool)`: `true` in `Node.Run` (device, supervisor in the root namespace), `false` in workers (nothing routes into their TUN, and `SO_MARK` needs `CAP_NET_ADMIN` over the namespace, which older kernels check in the root user namespace). `map applied` logs `route_table_routes`; the local API's counters add `router.direct`, `route_table.routes`, `route_table.reapplies` (`thinkpol status` prints a route table line).
- Dev map spec: `chains: [{name, exit}]`, `rules: ["<match> -> <action>", ...]`, `presets: {domestic, chain}` go into every device's section; a `geoip:` rule or `presets.domestic` must name a spec list (TP-017's `lists`), and every device must name it in its own `lists` (the builder says so otherwise). The reference spec and golden show it all (device-b now has a path to server-3, the chain's exit, and the `ru` list).

*Performance* (lab node, an RU-sized set: 12,895 IPv4 /24s + 10,088 IPv6 /32s, none mergeable, plus the local ranges: 22,997 routes since the review's IPv4 fallback; `TestCountrySizedTable`). After the review, on a quiet host: connect 0.34–0.37 s, one endpoint moved 0.07 s, switching to "everything" 0.37 s, back 0.29–0.31 s, disconnect 0.31–0.36 s (an idle Docker VM; earlier runs shared it with other labs). Before the review, on a quiet Docker host: connect (first Apply) 1.65 s; a map moving one endpoint 0.30 s (one dump of the table and a diff); a gateway change: no route touched, one no-op re-apply; switching to "everything" (removing the country) 2.6 s; back 1.3 s; disconnect (Close) 1.3 s. With another project's load lab on the same host the same steps took 3.9–5.1 s, 0.4–0.6 s, 4.8–5.1 s, 4.3–7.5 s and 4.0–8.9 s: the cost is netlink round trips, so it scales with CPU contention. Netlink costs ~60 µs per IPv4 add and ~90 µs per IPv6 delete; with the watcher subscribed during the Apply it was twice that, hence the pause. Batching netlink requests (many per `sendmsg`, ACKs read after) would cut it if ever needed; while it runs, direct destinations being removed enter the TUN and are dropped (never leaked), and new ones still go through the tunnel until thrown. The engine holds its lock during the Apply, so `Status` waits that long on connect.

*Gotchas:* `ip rule show protocol N` is not a filter in the lab's iproute2 (it lists every rule): check rules by priority. `ip -6 route get` to an unreachable route says "No route to host". Throw and unreachable IPv6 routes show `dev lo` in dumps; netcfg compares them by type only.

- **TP-023 (M1 acceptance):** `lab/routetable_test.go` is the base for "direct vs tunneled"; once TP-014 merges, assert the foreign site answers through server-1. Lab networks are private ranges, which `local` (in every preset) sends around the tunnel: test sites need public-looking addresses (the test puts documentation addresses on lo and routes them on both routers).

## Review findings
Two reviewers; orchestrator decisions.

- [x] B1 A TUN going down and up silently removes the IPv4 default in table 0x7470 (no RTM_DELROUTE for IPv4): foreign IPv4 leaks direct, is never repaired, and status still says enforced. Watch RTNLGRP_LINK for the TUN (up/down/index change) and re-apply; re-apply also when the last re-apply failed; a cheap periodic re-apply as a backstop; Status shows enforcement failing (Enforced=false + last error) and `thinkpol status` reflects it. Lab: `ip link set <tun> down; up` → table restored, no foreign IPv4 at the router.
- [x] B2 TunnelVision (CVE-2024-3661): narrow rule 5300 so only the overlay prefixes and the physical interfaces' on-link subnets (mirroring main's `proto kernel scope link` routes) are looked up in main ahead of table 0x7470; every other main route (DHCP option-121 /1 routes, other VPNs' splits) no longer beats the tunnel. Needs `Dst` on `netcfg.Rule`. IPv6 the same, so a non-default IPv6 route in main can't beat the unreachable default with a v4-only overlay (D6). DESIGN and Notes ("IPv6 never leaks" must be true). Lab: `0.0.0.0/1` + `128.0.0.0/1` via the physical gateway in main → foreign traffic still enters the TUN; an IPv6 specific route in main with a v4-only overlay → IPv6 still unreachable.
- [x] B3 A crash, then a restart disconnected or removed: leftover proto-86 rules and routes stay. At a device's start when not connecting, open `netcfg.New(OwnerRouteTable)` and Close it (or make the Enforcer per node). Lab: kill -9 while connected, restart disconnected → rules and table 0x7470 gone.
- [x] B4 Kernels < 4.17: after the first RuleAdd, dump and verify our rules came back with protocol 86; if not, delete them by exact match and return ErrUnsupported ("needs Linux 4.17"). Unit test the detection path.
- [x] F5 DESIGN and the ws ticket's Notes: endpoint throws cover the whole IP; for CDN-fronted endpoints narrow them to the transport's flow (proto/dport rules). Note only.
- [x] DNS: mark the resolver's direct sockets (TP-020's `dns.Options.Control`) if TP-020 merges first; otherwise a precise Note in both tickets.
- [x] Nits: snapshot the Want under the lock and Apply outside it (Status mustn't block for seconds); a cancellable ctx for recompileRules; a status hint when Tailscale-style rules sit ahead of ours.

Resolution:
- B1 Watch also takes link events (any link added, removed or changing flags; flagless wireless events ignored) and main's kernel on-link routes; the enforcer re-applies on them, every minute (`Backstop`) and every 5 s while the last attempt failed. An `unreachable` default now sits behind the TUN's for IPv4 too, so a TUN that is down or gone drops foreign IPv4 instead of leaking it until the re-apply. `routetable.Status{Enforced, Error}` → `dataplane.RouteTableStatus` → health problem `route_table_not_enforced` (down) in `thinkpol status`. Tests: `TestEnforcerAppliesChangesAndReappliesOnEvents` (failed re-apply in the status, retried), `TestEnforcesInANamespace` (TUN down: unreachable, status not enforced; up: put back), netcfg `TestWatchSeesGatewayChangesAndOwnRemovals` (link down/up/added, an address's on-link route), lab `TestRouteTableSendsOnlyDirectAroundTheTunnel` (TUN down and up: nothing to the foreign site at the gateway, the status says not enforced, the TUN's route comes back).
- B2 Rule 5300 is now `to <prefix> lookup main` for the overlay networks (`Want.Overlay`) and the trusted on-link subnets (`netcfg.Survey.OnLink`, filtered by `routetable.TrustedOnLink`: local ranges, IPv4 ≥ /24, IPv6 ≥ /64); `netcfg.Rule.Dst`. Tests: `TestConfigLayout`, `TestTrustedOnLink`, `TestEnforcesInANamespace` (0.0.0.0/1 + 128.0.0.0/1 via the gateway and an 8.8.4.4/8 address: 8.8.8.8 still tunneled; 2000::/3 in main with IPv6 off: still unreachable), netcfg `TestSurveyFindsOnLinkSubnetsAndForeignRules`, lab (split routes in main: the foreign site still enters the TUN; 2000::/3 in main with a v4-only overlay: unreachable). - DNS TP-020 is still in review on its branch: Notes here say what to wire (`dns.Options.Control` = `routetable.SocketControl()` in `agent.(*runner).newResolver`); TP-020's ticket already says the same from its side.
