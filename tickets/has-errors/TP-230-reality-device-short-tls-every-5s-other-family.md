## Goal
During the censor matrix's reality holds (TP-223's runs, 2026-11-16), device-a opened about 92 short TLS connections to the server's port 443 over IPv4, one every ~5 s, each completing a handshake and closing, while the link itself rode IPv6. A fixed 5-second pattern of short handshakes is a fingerprint a censor on the path can see. Find what opens them (path probing of the other family, a dial loop, a health check) and decide whether it is needed.

## Scope
- Find the code that opens these connections, with evidence from a lab hold.
- Propose to the owner whether to remove or reshape the pattern, or accept it as a residual risk.

## Out of scope
- Any product change before the owner has seen the fix's scope.

## Acceptance
- [x] The code that opens these connections named in Notes, with the evidence (a capture or the trace from a lab hold). Notes, round 2 (the traces of three holds) and Fix; this branch's lab run on the pre-fix code shows server-1's "serving the map failed, retrying … reality [::]:443: … bind: address already in use" every 5.0 s (Log).
- [x] Either the pattern is removed or changed so it no longer forms a fixed short-handshake rhythm, with a lab check that would catch it coming back, or the owner accepts it as a residual risk with a RESIDUAL-RISKS.md row. ### Fix (2026-11-22): options 1 and 2's bind-before-check, plus a backoff of failed target checks

Scope chosen by the orchestrator; the owner hasn't approved the product change yet, so the branch stops at review.

- **Bind per family** (`internal/dataplane/transport/reality/listener.go:98`, `listenNetwork`): an IPv4 address binds `tcp4`, an IPv6 one `tcp6` (Go sets IPV6_V6ONLY for it), as udp does. `0.0.0.0:443` and `[::]:443` both open, so the apply succeeds and nothing retries.
- **Bind before the check** (`listener.go:64`, `openListener`): Listen first binds its address and closes that socket at once, then `checkTarget` (`listener.go:107`) reads the roots and checks the target, then it listens. A listener that can't bind never dials the target. The first version held the bound socket through the check; the reality matrix's `active prober` cell failed on it twice (the prober's replay to server-1's IPv4 :443 got no answer) and passed with the fix reverted. Held, the port took connections into its backlog and answered none for the check's ~5 s (a tell of its own), and the supervisor then handed them all over at once as it started serving, apparently before its worker knew the listener: device-a's first IPv4 dial got "TLS handshake: EOF" 7 ms before the worker logged "listening shared 1". Closing the probe leaves the port closed while the check runs, as before the fix.
- **Back off failed checks** (`internal/dataplane/transport/reality/targetcheck.go:50`, `targetChecks.run`; `:81`, `checkBackoff`): a binding listener whose target check fails (target down, certificate wrong, detection stalled) would still be retried every `RetryAfter`, each retry a dial. So a failed check keyed by target and server names isn't run again before a wait drawn from the upper half of 10 s, doubling with each failure in a row up to 10 minutes; meanwhile Listen fails at once with the last error and dials nothing. A check cut short by its context doesn't count.
- **A passed check isn't cached**: not needed. The supervisor (`setListeners`, `internal/agent/supervisor/shared.go:362`) and a device's listener set (`internal/agent/dataplane.go:957`, `listenerSet.reconcile`) keep a listener that opened across retries, so a retry of an apply that fails for another reason reopens only the failed listeners and never re-checks a target that passed. A process-wide cache of passed checks would also hide a target that went bad until restart.
- **Other TCP listeners the agent opens**, checked for the same collision: the blob service (`internal/dataplane/blobs/serve.go:166`) and the DNS resolver (`internal/dataplane/dns/server.go:270`, UDP at `:266`) bind the node's overlay addresses (or the one tuning address), never a wildcard pair; the local API is a unix socket. The only transports are udp (fixed in TP-004), reality (fixed here) and memory (in-process). openvpn-tcp, random-tcp and the relay are the lab matrix's reference rows, not agent listeners. REALITY's camouflage splice dials, it doesn't listen.
- Docs: `reality` doc.go (binding, its order and the backoff), docs/design/transports.md, lab/README.md (the new check).
- Found on the way (out of scope): a server's status reads the map applied and not retrying while its first apply still opens the listeners and checks the target. `mapApplied` passes then, which is why the matrix's reality setup never caught this bug. The new lab check waits for the supervisor's "map applied" log line instead.

### Investigation, round 2 (2026-11-22): the cause

**The connections aren't device-a's.** They are server-1's TLS handshakes with its own camouflage target, made by a public reality listener that can never bind and is retried every 5 s. The title and Goal misread the flow: TP-223's note took the flow's client for device-a, but the client is server-1 and the server is the camouflage site.

Evidence: the `wireguard-rhythm` traces (`THINKPOL_LAB_TRACES`, one JSON line per application-data record) of three earlier reality holds. These are TP-223's two (2026-11-16, at 02284b57: in use, and idle) and one held run of 2026-11-18. Today's lab run couldn't build the lab image (see Log).
- Each trace has exactly 92 short connections, every one on the same address pair. The pair's client is server-1's IPv4 address, and its server is the camouflage node's port 443. Server-1 is the one address that also opens REALITY's target dial for device-a's connection, with the same host number as server-1's IPv6. In the 2026-11-18 run it is also the address device-a's later IPv4 link was dialed to and accepted on. No short connection has device-a's address on either end.
- Every short connection has the same records. The server sends 6: EncryptedExtensions of 27 bytes, the certificate, CertificateVerify, Finished, and two session tickets. The client sends 2: Finished (53) and close_notify (19). So the client completes the handshake and closes it at once. REALITY's target dial for device-a's own connection has EncryptedExtensions of 36 bytes. The 9-byte difference is exactly an ALPN extension for `h2`: device-a's hello (utls Chrome) offers ALPN, and these hellos offer none.
- The gaps are 5.008 to 5.086 s, which is a 5 s timer plus a few milliseconds of work. The first short connection comes about 3 s before device-a's link exists (device-a starts after server-1), and the pattern runs to the end of each hold.

The code:
- With no `listen:` written, the map builder derives one listener per transport, port and address family from the endpoints: `reality 0.0.0.0:443` and `reality [::]:443` (`internal/devmap/spec.go:812`, `listenersFor`).
- Reality's `openListener` binds with `lc.Listen(ctx, "tcp", addr)` (`internal/dataplane/transport/reality/listener.go:86`). On plain `"tcp"`, Go makes a wildcard address one dual-stack socket. `0.0.0.0:443` therefore binds as `[::]:443` and takes both families, and `[::]:443` then fails with "address already in use". Checked with a standalone Go program on loopback: `0.0.0.0:p` reports `[::]:p` and accepts a dial to `[::1]:p`, and a second Listen on `[::]:p` gets `bind: address already in use`. The udp transport hit this exact collision and pins the family (`listenNetwork`, `internal/dataplane/transport/udp/transport.go:147`, TP-004, with the lab test `TestListenWildcardsOfBothFamiliesOnOnePort`). Reality never got the same fix.
- `openListener` checks the target before it binds. It calls `verifyTarget` (`listener.go:79`), a crypto/tls handshake with the target for each server name: no ALPN, `MinVersion` TLS 1.3, closed right after (`listener.go:435`). It then runs `detect`, whose result REALITY caches per process, and only then calls `Listen`. So every failed bind costs one full TLS handshake with the target.
- The listener that fails makes `serverSpaces.apply` return `errListeners` (`internal/agent/node.go:1001`, from `Supervisor.SetListeners`, `internal/agent/supervisor/shared.go:379`). The run loop retries the whole apply after `RetryAfter`, 5 s (`internal/agent/dataplane.go:144`; `node.go:1054` and `:1095`). Each retry calls `SetSpaces` again and reopens the missing listener: `verifyTarget` → one handshake, then EADDRINUSE again, for as long as the node runs. Each failure logs a warning ("serving the map failed, retrying"), and the server's status says `retrying` the whole time.

Why every ~5 s? `RetryAfter` is a product constant on the wall clock. It is not one of the WireGuard timers the lab speeds up (TP-251), so the rhythm is the same at real time and in a scaled lab; this case needs no real-timer run.

Is it needed? No. It is a bug. The listener that keeps failing adds nothing: the dual-stack socket of the first one already accepts both families, which is why nothing visibly broke. Device-a's IPv6 link and its later IPv4 link were both accepted on it. Stopping the retries breaks nothing, as long as both families still listen.

What it costs, and what a censor sees:
- From the server's uplink, a censor sees the server's address open a TLS 1.3 connection to the camouflage site every 5.0 s, around the clock (about 17,000 a day). Each one is a Go crypto/tls ClientHello (no ALPN, Go's fingerprint, not a browser's), a complete handshake, then a close. The camouflage site's operator sees the same thing.
- It ties the server to the site its clients name in their SNI, even when no client is connected.
- It hides REALITY's upstream tell from the prober. These are the "server-1 dials the site outside the probes" that make reality's prober cell unattributable (TP-223 round 4, TP-255). They come from server-1 itself, not from device-a.
- It happens on any dual-stack server whose map derives its listeners (endpoints of both families and no `listen:`), not only in the lab.
- The server's log gets a warning every 5 s, its status shows `retrying` for good, and every retry also re-runs `SetSpaces`. I haven't measured what that re-run costs.

No lab run was possible today, so server-1's warning line itself is not seen directly. The first lab run once the image builds again should show "serving the map failed, retrying" with "address already in use" for `reality [::]:443` every 5 s in server-1's log (`thinkpol logs` in the node). This ticket names nothing about device-a's first dial: in two of the three runs, device-a's first link rode IPv6 though the map lists IPv4 first, and these traces can't say why (a refused or unanswered SYN leaves no records). That is out of scope here.

Options for the owner:
1. **Fix the bind (a bug fix).** Reality listens per family, `tcp4` for an IPv4 address and `tcp6` for an IPv6 one, as udp's `listenNetwork` does. Both listeners open, the apply succeeds, and nothing retries. Cost: S. It is one function in the reality package, a lab test like udp's `TestListenWildcardsOfBothFamiliesOnOnePort`, and a lab check that would catch the pattern coming back: after setup, server-1's status isn't `retrying`, and during the hold server-1 opens no connection to the target that isn't REALITY's dial for a client connection. A censor then sees target dials only when clients connect: one at each listener open, then REALITY's own dial per connection, which is the accepted RR row.
2. **Harden the retry as well (with 1, or as a follow-up).** Bind before checking the target, or keep a target check that passed per target for the process, as `detect` already does. Then a listener that keeps failing for another reason (the port taken by another program, a typo in the map) doesn't redial the target on every retry. Also back off failed listener retries from 5 s to minutes, with jitter. Cost: S to M. Trade-offs: binding first briefly holds a port that may close again if the target check fails, which resets clients that connected meanwhile; a cached check can go stale until restart.
3. **Back off only.** The retries get slower but stay periodic, the second listener still never opens, and the status still says `retrying`. It hides the bug rather than fixing it.
4. **Accept it with a risk row.** Not worth it: the fix is cheaper than the row, and the tell is a fixed 5 s rhythm from the server's own address.

Recommendation: option 1 now, with option 2's bind-before-check in the same small branch, so that no failing listener can rebuild the rhythm. The backoff can wait for a follow-up. Once fixed, reality's prober cell loses its background dials. It stays `not judged` by design (upstreamTell is `report`), but its detail will count far fewer dials outside the probes.

### Investigation (2026-11-16, partial: code reading only, no lab evidence yet; superseded by round 2 above)

What the code settles:
- The only TLS client a device has is the reality dialer, `internal/dataplane/transport/reality/dialer.go:25` (the listener's `verifyTarget` is the server's, toward its target). Its only caller is the path layer's dial loop, `internal/dataplane/path/link.go:518`, in `startDial` (`link.go:510`). No health check, prober or second client exists on a device: so these connections are path-layer dials.
- One dial loop per dialed neighbor (`Node.Update`, `internal/dataplane/path/node.go:219`, keyed by node id). It dials the neighbor's endpoints in map order; `lab/maps/reality.yaml` lists server-1's IPv4 endpoint first, IPv6 second. A dial that fails, or whose link is never proven, moves to the next endpoint after a backoff of 250 ms doubling to `RedialMax`, **5 s** (`node.go:71`, `link.go:549`, `link.go:557`). A proven link that dies restarts from the first endpoint (IPv4). The 5 s matches the observed rhythm; the agent's `RetryAfter` (`internal/agent/dataplane.go:143`, a failed data-plane start or Apply) is also 5 s and is the other candidate.
- A dial spliced to the target completes the TLS handshake with the target's certificate, then fails with `ErrNotAuthenticated` and closes at once (`dialer.go:74`): exactly "a short TLS connection that completes its handshake and closes". The server dials its target on every accepted connection, authenticated or not (package doc), so the camouflage dials appear either way.

What it doesn't settle: a dial loop that holds a live link waits on it (`link.go:524`) and dials nothing, so one loop can't dial IPv4 every 5 s while it holds the IPv6 link. One of these must be true, and the lab run decides which:
  (a) the loop is in a failure run and the IPv6 connection that carries traffic is a link it never counted as proven (`neighbor.pick` sends on an unproven link, `link.go:57`); or
  (b) something starts a second engine/dial loop every 5 s that dials the first endpoint and is torn down (a data-plane start or Apply retried every `RetryAfter`); or
  (c) IPv4 dials are spliced by the server (unrecognised hello) and the loop's IPv6 link keeps dying and restarting from IPv4 (would show many IPv6 connections too).

Reproduction, ready to run: `make lab-gotest PKG=./lab 'RUN=TestCensorMatrix/^reality/^(off|wireguard-rhythm)'` (no `$` anchors: make expands `$/` to nothing and the run matches no cell). During the 450 s hold, inside the lab's containers: `ss -tni '( dport = :443 )'` in device-a once a second, a capture of TCP 443 SYN/FIN/RST per family on the router, and `thinkpol status` in device-a (its neighbor's links: endpoint, dialed, up). Device-a's info log names the first failed dial of a run (`dial failed` with the error: `the server didn't authenticate` means spliced, `no answer within 6s` means an unproven link) and every `link up` / `link closed`.

Outside the lab: nothing in the dial loop is lab-specific. Any device whose neighbor lists several endpoints (a dual-stack server lists both families) runs the same loop, so (a) and (c) would happen wherever one endpoint keeps failing; whether the IPv4 endpoint fails only because of the lab's topology is for the run to show.

Options (to price once the cause is known):
1. Don't dial other endpoints of a neighbor while a link to it is up, and back a failing endpoint off far past 5 s (minutes, with jitter). Cheap (dial loop only); risk: failover to a dead family's sibling waits on the backoff.
2. Jitter the redial backoff and raise `RedialMax` to minutes for every loop. Cheapest; still a periodic pattern, only slower.
3. Find and remove the second dialer if it is (b): a bug fix, no trade-off.
Recommendation pending the lab evidence; the leaning is 3 if (b), else 1.
