## Goal
`thinkpol diag` writes one snapshot of everything the agent changed on the host and what the host shows of it. That snapshot is the evidence a real-device run records and an agent judges afterwards. Device checks shrink to "do the step, save `diag` and a capture". The parsing and judging that the device-test kit did in bash now lives in Go: it is tested, and it ships to users for support.

## Scope
- A local API call and a `thinkpol diag` command that print a versioned JSON snapshot (`-o FILE` writes it at mode 0600). The snapshot holds:
  - the status the local API already serves;
  - the routes, rules and addresses the agent owns, as the host reports them;
  - the IPv6 leak guard:
    - on macOS: the pf anchor's rules with their counters, the exempt table, the agent's `pfctl -E` reference and whether pf still holds it, and pf's enabled state;
    - on Linux: the nftables guard table with its counters;
  - DNS: the resolvers the host uses for the overlay's domains and for everything else;
  - the TUN: its name, MTU, addresses and state;
  - the last Apply's steps with their timings.
- Every field the agent cannot read says why (`"unreadable": "<reason>"`), never just empty, so a judge can tell "nothing there" from "couldn't look".
- No secrets: no keys, tokens' secret parts, or session ids. Endpoints and addresses are in, because the user is the one reading them.
- Read-only: `diag` changes nothing on the host. Unprivileged callers get what the socket's permissions allow.

## Out of scope
- Judging the snapshot (PASS/FAIL). That's done after a run, by an agent reading the snapshot and the capture. If a judgement repeats often enough to code, it goes into the lab or a Go test over recorded fixtures, not into a device script.
- Windows (TP-047 adds its parts).

## Acceptance

- [x] a test checks that no secret field from the config or status reaches the snapshot (`TestDiagnosticsHoldNoSecret`, `TestTheSnapshotHasNoSecretField`, and the lab test's key check)
- [x] the snapshot carries a schema version; docs/design/desktop-client.md "The local API" describes it (`schema_version` 1, `localapi.DiagSchemaVersion`; its one line points to the localapi package doc, which holds the mechanism)

## Notes
- **Origin (2026-10-16).** The private device-test kit for TP-078 grew to about 10,000 lines of bash against about 3,000 lines of product change (tests included), most of it judgement logic: parsing tcpdump and pfctl output and deciding PASS or UNKNOWN. Its stub tests could never reach real root, routes or tcpdump, so every review round found new ways a check could PASS wrongly. See ORCHESTRATION.md "Device testing (2026-10-16)".
- After this ticket, TP-078's checks 08 and 10 reduce to `thinkpol diag` before, during and after, plus a capture.
- **Where it lives.** The mechanism is in `internal/agent/localapi/doc.go` ("Diagnostics"), with each reader in its package's doc: `netcfg` ("Reading back"), `firewall` ("Linux: reading it back", "macOS: reading it back"), `dns` ("Reading back"), `dataplane` ("The last Apply's steps"). docs/design/desktop-client.md "The local API" names `diag` as the one exception to "nothing the API reports is a public address", and docs/design/security.md's local API line says the same.
- **Root only.** The routes, rules, guard and resolvers name public addresses, so the group's snapshot has them unreadable ("root only") and the agent doesn't read them for it; the status, the TUN and the last Apply are the group's too. The pf reference shows by its pid; its token stays in the record.
- **Device run (the owner's, after review round 1).** Nothing here ran pfctl or scutil. On the Mac, connected with the guard applied, record: before each step `date -u +%FT%TZ >> times.txt`, and once after the last.
  1. `sudo ./bin/thinkpol diag -o diag-connected.json`; as a non-root member of `thinkpol`, `./bin/thinkpol diag > diag-member.json 2> diag-member.err` (on macOS the member may be refused, TP-094: keep the stderr either way).
  2. Each to its own file: `sudo cat /private/var/db/thinkpol/pf-guard.token` (the guard's record: the token stays out of the snapshot), `sudo pfctl -a com.apple/000.thinkpol -s rules -v`, `sudo pfctl -a com.apple/000.thinkpol -t thinkpol_exempt6 -T show`, `sudo pfctl -s info`, `sudo pfctl -s References`, `sudo pfctl -s rules`, `sudo pfctl -s Interfaces -v`, `sudo pfctl -a com.apple -s Anchors`, and `scutil --dns` (all listings).
  3. `sudo ./bin/thinkpol disconnect`, then `sudo ./bin/thinkpol diag -o diag-disconnected.json` and step 2's `-s rules -v`, `-s info` and `-s References` again.
  4. `sudo chown "$USER" diag-*.json` (written 0600 by root), so the owner and the judging agent can read them.
  **Judged afterwards, by an agent, not during the run:** no `unreadable` in `guard`, `routes`, `dns` (`policy_rules` empty); `guard.rules` the same lines as `-s rules -v`, their counters the same within the seconds between them; `guard.exempt` the `-T show` entries; `pf.guard_check.main_rules` what `-s rules` lists up to the hook; `pf.reference` held while connected and not recorded after the disconnect; the post-disconnect `-s References` no longer lists the token the record named while connected, and whether it printed its header (pfctl may print none when pf holds no reference: the guard then can't read the listing, so its Close fails and keeps the record, which would show in the disconnect's log and in `pf.reference`); `dns` the resolvers `scutil --dns` lists; the member's snapshot `host_parts: false` with the host parts "root only", or its refusal in the stderr. The listings go into `firewall/testdata/pfctl` and `dns/testdata/scutil`, replacing the built ones; a parse failure is a finding. Then the two macOS boxes can be ticked.
- **Decisions (round 2).** The JSON is v1 with the proto's own names (snake_case) and every field, written by `WriteDiagnostics` for `diag` only: `status -json` keeps its camelCase form. The TUN reader lives in `netcfg` (`InspectInterface`), the host side of the overlay. A server's TUN and last Apply say so (`UnreadableServer`): its data planes run in its workers, which the status lists. The pf token never enters the snapshot.
