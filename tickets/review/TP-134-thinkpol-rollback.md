## Goal
A user (or the device-test harness) whose agent crashed can put the host back with one root command: no routes, guard, pf reference or resolver configuration of thinkpol's left.

## Scope
- `sudo thinkpol rollback`: under the host lock (refused while an agent runs), run the agent's start-time cleanup (`agent.Platform.ClearHost`, the same `up -connect=false` runs), report what it undid and what is left. With the persisted connect state (TP-046) and the kill switch (TP-048), say what rollback means for a device that should stay fail-closed after a crash: rollback is the user choosing to go back to no tunnel.
- The same command serves the harness's last-resort restore (TP-082) and the docs' crash recovery, replacing the by-hand route deletions in the runbooks.
- TP-132 (uninstall after a server crash) may share it: say which owns the supervisor's cleanup.

## Notes
- Owner's answer to the device-harness questions (2026-10-23, TP-082 question 4).
- **What rollback is** (implementer, 2026-11-12). `agent.Rollback`: as root, under the host lock (refused with nothing touched while another thinkpol process holds it: a wrapped `ErrAnotherAgent`, exit 75), first this boot's connect choice recorded down (so a rollback cut short still settles it), then the parts `Platform.ClearHost` clears, one `HostPart` each (a server's leftovers where a server runs, the route table with its leak guard, the overlay, the resolver configuration, the kill switch with its place named per OS, `firewall.KillSwitchPlace`), every part tried whatever failed. A start decides whether to connect under the same lock (`Node.Adapters`), so a start the service manager began during a rollback follows its record. The record is "the crash posture TP-048 leaves": without it the service's next start in the boot follows the record (meant up) and puts the kill switch back. With it the start comes up disconnected; only the toggle, on, puts the kill switch back, in the down shape (said in the report). The report says per part `none left`, `undid: …` (a server's, as uninstall) or `LEFT: …`, how the choice was recorded, and with nothing left that traffic goes direct and whether a service's next start puts the kill switch back (the toggle, read from the node's state directory; a server's worded for a server); exit 1 when anything is left (`errRollbackLeft`) or a device's choice wasn't recorded (`errRollbackNotRecorded`). The service is neither stopped nor removed; a hanging start holds the lock and is stopped first (security.md). `service uninstall` gets the same parts flattened (`ClearHost`), each failed one named once by its label, the server's last as before.
- **Who owns the supervisor's cleanup: TP-132** (decided here with TP-132's Notes). TP-132 built it (`supervisor.ClearLeftovers`, run as `ClearHost`'s server part, merged); rollback reuses it through the same `ClearHost` parts and adds nothing of its own for a server. A change to what a server's cleanup undoes goes to `ClearLeftovers`, which both commands share.
- The harness's last-resort restore (TP-082) and the private device kits' by-hand route deletions can call `sudo thinkpol rollback` now; changing them is TP-082's (not this branch's).
