## Goal
The matrix's wireguard-rhythm cells hold the tunnel 7.5 minutes of real time to see three rekeys (the reality and udp rows): the largest fixed wait left in a full lab. The owner's rule (2026-11-16): waits use a sped-up clock wherever possible. A system-wide fake clock can't reach a Go binary (libfaketime hooks libc; time namespaces only offset clocks), but the WireGuard these cells exercise is thinkpol's userspace wireguard-go, whose rekey timers are compile-time constants (device/constants.go).

## Scope
- A lab-only build replaces that constants file with timers scaled by a factor (10×) through a go.mod of its own (`go build -modfile` with a replace to a scaled copy of wireguard-go in the user cache; `-overlay` refuses files in the module cache), never touching the checkout's go.mod or the product binary.
- The censor's rhythm rules scale by the same factor, from one setting: the windows that are wireguard-go's timers (REJECT_AFTER_TIME and REKEY_TIMEOUT in the rekey window, the quiet, the pair window's cap); the persistent keepalive and the module's network choices keep real time.
- The scaled cells run in every lab.
- One real-timer run of the rhythm cells stays as its own target (`make lab-test-rhythm-real` or similar), run whenever transport shaping or the rhythm rules change; a full lab at real time (`THINKPOL_LAB_WG_TIMER_SCALE=1 make lab-test`) at milestone gates.

## Notes
- Only WireGuard's timers scale, and the hold's ping with them (R1.1). Reality's own timing, TCP and thinkpol's path probes keep real time, so each rekey comes with less of their noise around it: a signal that real-time noise would break can still fire in a scaled cell. Today's expected-fail cells fail by the same signals at both speeds (R1.2's attribution); a cell expected to pass (e.g. after TP-237's cover records) must be judged on the real-timer run.

- How (2026-11-19): `go build -overlay` refuses files beneath GOMODCACHE, so the lab's thinkpol build (lab/prepare.go `buildTools`, lab/wgtimers.go) reads a go.mod of its own (`-modfile`, in a temp dir, with the checkout's go.sum): the checkout's go.mod plus `replace golang.zx2c4.com/wireguard => <copy>`, the copy being the module with `device/constants.go` scaled, kept in the user's cache under its version and a hash of the scaled file, so the binary stays the same run to run. Only thinkpol's build gets it; labdns, censord, node package tests, go.mod and `make build` don't. Every duration constant of the file is divided (`(expr) / N`), RekeyTimeoutJitterMaxMs too (334 → 33 ms at 10, whole milliseconds), counts and sizes are left; MaxTimerHandshakes is written out as 90 / 5 and stays right. A constant missing, added or renamed fails the build. `THINKPOL_LAB_WG_TIMER_SCALE` (1 to 10 since R1.1, default 10) is read by the build and by the rhythm cells (`rekey` = 120 s / N, hold = 450 s / N + 10 s, so 55 s); `make lab-test-rhythm-real` runs the cells with 1.
- wireguard-rhythm: with a shorter `rekey` the windows that are wireguard-go's timers scale (REJECT_AFTER_TIME and REKEY_TIMEOUT in `window()`, the quiet, the pair window capped at scaled REKEY_TIMEOUT); the persistent keepalive in the window, count settle, burst gap and steady jitter keep real time (R1.2, R1.3, R1.9). At the default 120 s nothing changes.
- The scaled lab speeds up every lab test's WireGuard, not only the rhythm cells: product code derived from wireguard-go's constants scales with them (`dataplane.ExitHandshakeDeadline` = 3 × RekeyTimeout, 1.5 s at 10). WireGuard gives up a handshake after 9 s and drops a session after 18 s at 10. The real values are proven only by a full lab at scale 1, at milestone gates (lab/README.md).
- Wall times (under other sessions' load), `TestCensorMatrix/^(udp|reality)$/^(off|wireguard-rhythm)$`. Real timers (`make lab-test-rhythm-real`, 040d0d0e): udp/wireguard-rhythm 473 s, reality/wireguard-rhythm 482 s; rows udp 772 s, reality 895 s. Scaled ×10 (040d0d0e): 82 s and 82 s; rows 175 s and 187 s (an earlier scaled run at d13cecbd: 78 s and 76 s, rows 320 s and 321 s, the lab start slower under load). The matrix's longest row (reality) loses about 400 s of hold.

## Review findings
- [x] R1.1 (should-fix, proven) The scaled cell isn't the same experiment: at x10 KEEPALIVE_TIMEOUT is 1 s and the hold pings every 2 s, so wireguard-go sends a passive keepalive ~1 s after every reply, which a busy real tunnel never does; the record-count difference then steps +1 every 2 s and the count signal can never chain. Keep the hold's traffic in the same order relative to the scaled timers as at real time (ping interval below the scaled keepalive, count settle (300 ms) < ping interval < scaled quiet < scaled keepalive) and cap the scale at 10. Done: lab/results_test.go rhythmPing pings every min(2 s, 0.4 KEEPALIVE_TIMEOUT / scale), 0.4 s at 10 (300 ms settle < 0.4 s < 0.5 s quiet < 1 s keepalive), used by holdTunnel (lab/reality_matrix_test.go); lab/wgtimers.go maxWGTimerScale = 10. Proof with R1.2's.
