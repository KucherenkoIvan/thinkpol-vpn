## Goal
A shared listener the supervisor opens is served only once every worker knows its id, so an authenticated client's first connection after a server starts (or after a map adds a listener) is served, not dropped.

## Scope
- `sharedListeners.open` (`internal/agent/supervisor/shared.go:436-443`) starts `serveStreams` (or `serveDatagrams`) as soon as the listener opens, while `setListeners` is still opening the rest of the set.
- `SetListeners` signals each worker's `listenersChanged` only after `setListeners` returned (`internal/agent/supervisor/supervisor_linux.go:561-568`), so a worker learns the new ids later still.
- A worker that gets a stream for a listener id it doesn't know closes it (`internal/agent/worker/shared.go:190-194`, counted in `unknownListener`).
- Effect: an authenticated client whose first hello arrives during that window gets "TLS handshake: EOF" (on reality its target connection is dialed, then dropped). Probers are unaffected: what isn't authenticated is spliced in the supervisor. Seen in TP-230's lab runs as device-a's first IPv4 dial failing 7 ms before the worker logged "listening shared 1". Exists on rewrite.
- Fix sketch: `open` doesn't serve; `SetListeners` sends each worker its Listeners message synchronously (the worker acknowledges it), then starts serving the listeners it opened.

## Out of scope
- A server's status and "map applied" line coming before its listeners serve: TP-279.

## Notes
- Found in TP-230's fix round (2026-11-22).
- Design (2026-11-22): the worker answers each Listeners message with the ids it now has (`ipc.KindListenersKnown`, protocol version 6), sent from its control reader right after `sharedListeners.update`. Ordering on the control socket alone would cover streams but not datagrams (the data socket is separate), hence an explicit acknowledgement.
  - `shared.openListeners` (was `setListeners`) opens without serving and returns the ids it opened; `SetListeners` signals every worker, then `shared.serveOpened(opened)` serves those listeners once every served space that may be routed one (`ipcListeners`) has its worker attached and answered with it (`laggingSpaces`), whether that worker runs, starts or restarts (round 1: a worker not attached yet was skipped, R1.1). SetListeners has one caller at a time (the node's map loop).
  - The wait ends at `StopTimeout`: then the listeners are served anyway (one stuck space must not hold every other space's listener; that space's connections are refused until its worker is attached, as during any restart). Keeping them unserved and retrying was rejected for that reason. A worker taking longer than StopTimeout to come up still loses the first connection.
  - A new worker process is attached (routed to) only once it has answered for every listener it may be routed (`shared.attachKnowing`, under `s.mu`, so a listener opened later waits for it too); attach and detach wake the waiter. A Listeners message left unanswered for `StopTimeout`, counted from its send or from the last answer, kills the worker (exit `unresponsive`), attached or not (round 1: an attached one was never killed, R1.2). Answers are counted against the Listeners sent (`workerSockets.sendListeners`, `announceGained`'s TrySend included); an extra one is a protocol error (R1.3).
  - A listener closed while waiting is never served (it leaves `byID` under `s.mu`; `openListeners` and `close` wake the waiter). Listeners kept across a retry keep serving.
  - Ordering (R1.4, checked in Go's `internal/poll`): `Conn.Send` holds the descriptor's write lock while it waits for room, and `Conn.TrySend` (`RawConn.Write`) takes the same lock, so a socket's messages leave in the order their sends take it; a stream can't pass a Listeners sent before it on the control socket. `announceGained` relies on that (only stream listeners change with a space's transports, and streams travel on the control socket); a new listener needs the answers (datagrams go on the data socket, and workers not attached yet must be waited for). Documented in the package doc and on `announceGained`; no code change.
  - The prober path is unchanged: what isn't authenticated is still spliced or dropped in the supervisor; a listener not yet served leaves connections in its backlog for at most `StopTimeout`.

## Review findings
Round 1 (2026-11-22, on 80021b18): correctness (fix first), style (fix first), design (fix first), second opinion (fix first). Decision: keep the acknowledgement barrier (a per-route gate would drop or defer at route time, the very first-connection case), scoped to each call's own listeners, bounded by StopTimeout, with a worker that doesn't answer killed and restarted.
- [x] R1.1 Blocker: a worker started but not attached yet (a server's first map, or a restart) is skipped by `unacknowledged` (no route end), so the new listener is served at once and the first authenticated connection is closed for lack of a worker (`routeStream`), TLS EOF after reality's target dial. Detach doesn't wake the waiter either. Wait, up to StopTimeout, for every served space that may be routed the listener, attached or not; attach and detach wake. A test with a worker not attached yet that fails on 80021b18 (a real worker if the lab tests allow, else a fake that attaches late). Fixed: `laggingSpaces` counts a served space with no worker attached; `attach` and its detach wake (`shared.go`). Tests: `TestListenerWaitsForAWorkerNotAttachedYet` (starting, restarting; fake worker answering then attached late) and the real-worker `TestFirstDatagramAfterStartReachesTheWorker` (lab: the first datagram sent the moment SetListeners returns reaches the worker, NoWorker 0); the latter fails on 80021b18's code (run on d6694499: NoWorker 1).
- [x] R1.2 An attached worker that reads Listeners but never answers is never killed (`ackTimeout` is nil once attached), and the unattached timer counts from the session's start, not from the send. Arm the timer whenever answers lag, from the send or the last answer; kill and restart whether attached or not; factor the kill shared with `stuck`. A real-worker never-answering test that fails without the kill. Fixed: `session.serve` arms the answer timer whenever answers lag, re-arms it at each answer, kills through `session.unresponsive` (shared with `stuck`). Test: `TestWorkerNotAnsweringListenersIsRestarted` (lab, `runAnsweringWorker` answering only the first Listeners): killed 3.0 s (StopTimeout) after the second SetListeners, restarted; it fails without the kill (run on d6694499, the old code: never killed).
- [x] R1.3 An unsolicited ListenersKnown is accepted (a flood, or an answer ahead of its Listeners that masks lag). Count answers against the Listeners sent, `announceGained`'s TrySend included; an extra answer is a protocol error. Test plus mutation. Fixed: `workerSockets.sendListeners` counts before sending (session and `announceGained`); `shared.setKnown` refuses an extra answer, `readControl` ends on it (protocol error). Tests: `TestAnswerToNoListenersIsAProtocolError` (unit) and `TestUnsolicitedListenersAnswerIsAProtocolError` (lab, a worker answering twice: exit `protocol_error`; fails on d6694499).
- [x] R1.4 TrySend doesn't take SendTimeout's lock: can a stream pass an in-flight Listeners? Verify the reachable cases, fix or document; say why `announceGained` relies on ordering and SetListeners on answers. Fixed: `serveOpened(ids)` serves only the ids its call opened; SetListeners' doc says it has one caller. Test: `TestServeOpenedServesItsOwnListeners`.
