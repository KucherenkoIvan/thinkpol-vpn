# Agent instructions

What the project is: [README.md](README.md). [PRD.md](PRD.md) says what it must do and [DESIGN.md](DESIGN.md) says how; they are the source of truth. Don't contradict them in code: if they're wrong, fix them in the same branch and say so in the ticket's log.

Your task's prompt may override the workflow and conventions below, never the hard rules. If your prompt conflicts with this file, say so in your report.

## Hard rules

1. **Privacy.** The repo is public and personal. Never reference the author's employer, work projects, internal repository or package names, or copy content from other private codebases, in code, docs, comments, commit messages or examples. No absolute local paths or machine specs either. Grep the staged changes before every commit and scrub any hit. When unsure whether a term is safe, don't write it.
2. **Never touch the host's network stack.** No changes to the host's interfaces, routes, DNS, firewall or sysctls, not even "just to test". Linux networking code (network namespaces, netlink, nftables, NFQUEUE, TUN) is tested only inside lab containers.
3. **There is no CI: you are the CI.** `make lint` and `make test` must pass before every commit, plus the lab checks a ticket names. `make lint` vets every OS and builds the mobile packages, so a green run on a Mac covers Linux and Windows files too.
4. **No cgo in the data plane.** Everything under `internal/dataplane`, `internal/netmap` and `internal/lists` is pure Go, and all of it except `tun`, `egress` and `firewall` builds for Android (`make lint` checks both). Everything builds with `CGO_ENABLED=0` by default; only `cmd/thinkpol-tray` may use cgo.
5. **Dependency direction** (depguard-enforced, see DESIGN.md "Repository layout"): `dataplane`, `netmap`, `lists` and `agent` never import `features` or `shared`; `dataplane`, `netmap` and `lists` don't import go-kernel; `features` never import `dataplane` or `agent`; `shared` never imports `features`. **A new feature adds its own depguard rule** in `.golangci.yml` denying the other features (there's an example there).
6. **Protobuf lives in `proto/`**, a buf module; `proto/gen/` is generated by `make proto` and never hand-edited. Never in go-kernel's `contracts/`: a deliberate thinkpol-only exception, see DESIGN.md "Kernel usage".
7. **Personal infrastructure is off limits.** Never write anything about the owner's own servers or accounts (hostnames, SSH aliases, IP addresses, hosting providers, or what they run) in code, docs, tickets, commit messages or examples; use documentation addresses (`192.0.2.0/24`, `2001:db8::/32`) and `example.net`. Never connect to a remote host (ssh, scp, curl, anything) unless your task explicitly names it and says what you may do there.
8. **The development machine is someone's daily computer.** No `sudo`, nothing run as root, no system-wide installs or settings changes. Docker is shared with other work: create lab resources only through the `make lab-*` targets, respect the lab concurrency limits your task gives you, and remove only the `tplab-*` resources you created.
9. **Private notes stay private.** `comms/` is ignored by git: never commit it, and never quote it or point to it from tracked files.

## Workflow

- **Tickets.** Work comes from the board in [tickets/](tickets/README.md); follow its rules for moving tickets exactly, and the rules for running the board in [ORCHESTRATION.md](tickets/ORCHESTRATION.md#decisions-2026-10-10). One ticket, one branch (`<id-lowercase>-<slug>`), cut from `rewrite` and merged back into it only after review.
- **Worktrees.** Each ticket branch gets its own worktree at `../.worktrees/<repo>/<branch>`, relative to the main checkout. Don't work in the main checkout: it is reserved for board ops and serial merges into `rewrite`.
- **Push.** Ticket branches and `rewrite` live on `origin`; push a ticket branch as soon as it exists and after every commit.
- **Commits.** Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`).
- **go-kernel** is the control plane's kernel and is public: no `GOPRIVATE` or SSH setup. Its own rules apply to `KRN-` tickets, which are worked in go-kernel's repo.
- **Shared memory.** If a `recall` MCP server is available, start by calling `pack` with the keywords `project:thinkpol-vpn`, `start-here` and your ticket id. Store durable findings (gotchas, root causes, decisions and why) as you learn them, one small topic each. Never store secrets or anything rule 7 forbids.

## Conventions

- English everywhere. Name things for what they are; the mechanism should be readable from the name.
- **Commands.** `cmd/thinkpol` has one file per command, registered from `init` with a space-separated path. A command group is just a shared prefix: adding `dev lists build` is one new file. A group prefix is never itself a command (`register` panics). Command files are composition roots: they parse flags (`parseFlags`), build adapters and call into `internal/`, with no logic of their own. Internal commands (e.g. `worker`) are `hidden`.
- **Control plane** features follow go-kernel's [service structure](https://github.com/KucherenkoIvan/go-kernel/blob/main/docs/architecture/1-service-structure.md), with `ddd.DomainError` values for expected failures. The **data plane** is plain ports and adapters, no DDD aggregates.
- **OS-specific code** goes in per-OS files (`_linux.go`, `_darwin.go`, `_windows.go`) inside the package it belongs to; there is no platform tree. Android counts as linux for build tags: `_linux.go` files are in the Android build; desktop-only Linux code needs `//go:build linux && !android`.
- **Tests** assert behavior, not call sequences, and prefer real components over mocks. A test that needs root or network namespaces starts with `if os.Getenv("THINKPOL_LAB") == "" { t.Skip("needs the lab") }` and runs inside lab containers (`make lab-test` runs every package's tests in a lab node). Tests that drive several nodes live in `lab/` behind the `lab` build tag and declare the topology they need; see [lab/README.md](lab/README.md).
- Comments state non-obvious constraints only.

```sh
make help       # list targets
make lint       # gofmt, go vet + golangci-lint for darwin/linux/windows, Android build, no-cgo check, vulncheck
make vulncheck  # govulncheck per OS: known vulnerabilities in reachable code (needs the network)
make test       # unit tests
make test-race  # unit tests with the race detector (cgo on)
make build      # bin/thinkpol
make proto      # regenerate proto/gen
make tools      # pinned dev tools into bin/tools (lint and proto do it on first use)
make lab-test   # lab tests in Docker + every package's tests inside a lab node (needs Docker)
make lab-gotest PKG=./internal/x/...   # one package's tests inside a lab node
python3 tickets/board.py   # the board and what's ready to start
```
